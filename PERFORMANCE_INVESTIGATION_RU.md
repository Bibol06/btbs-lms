# Как мы исследовали задержки LMS — 15 ноября 2026

## Что проверяется

Отдельная временная PostgreSQL-база, 100 тестовых учеников, 10 курсов по 10 уроков. Четыре страницы API читаются через Nginx. Перед замером все ученики проходят одинаковый прогрев; измеренная нагрузка длится 30 секунд плюс завершение уже начатых запросов. Генератор — отдельный процесс Python на той же машине. Реальных учеников и SMTP тест не использует.

## Обнаруженная причина ожидания

До оптимизации программа курса под нагрузкой обрабатывалась внутри Django в среднем 550 мс, из них обращения к базе занимали 463 мс. Ещё 5993 мс в среднем приходилось на время вне приложения: очередь обслуживания, Nginx, сеть и чтение ответа. Нельзя точно назвать весь этот остаток временем очереди, но несколько секунд возникают до/вне относительно короткой обработки.

Представь 100 покупателей и 8 касс. Даже если обслуживание одного покупателя занимает полсекунды, покупатели в конце очереди ждут гораздо дольше. Redis хранит отдельные готовые данные каталога; он не отменяет проверку доступа, подсчёт прогресса и работу с базой.

SQL-время здесь включает ожидание PostgreSQL и передачу данных между Windows и Docker. Чтобы отделить медленный SQL от сетевых накладных расходов, на сервере нужно измерить планы запросов и повторить тест при близком расположении приложения и базы.

## Изменения

1. Добавлены измерения общего времени, времени приложения и SQL по каждому маршруту. Заголовки X-Bench-* используются только тестовым сервером, в рабочей LMS их нет.
2. Добавлен cProfile: он показывает, какие функции потребляют время. В прогретом последовательном профиле наиболее дорогие — «Моё обучение», программа курса и обновление прогресса.
3. При расчёте прогресса больше не читаются тексты уроков, описания заданий и объекты тестов целиком. Выбираются идентификаторы, типы шагов и проходные баллы.
4. Один список шагов повторно используется для расчёта процентов и отпечатка программы в истории прогресса. Удалено повторное чтение программы из базы. Число SQL для «Моё обучение»: 20 → 19.
5. Кэш оценок и прав доступа не добавлялся; они продолжают рассчитываться по текущим данным. Проверки регрессий сравнивают проценты, контрольные тесты, дедлайны и историю.

## Как повторить самому

Сначала зафиксировать сценарий и исходный результат. Затем сделать одно понятное изменение. Проверить правильность результатов тестами. Повторить тот же сценарий и сравнить одновременно ошибки, p95 и количество запросов. Увеличение числа обработчиков проверять отдельно от изменения кода.

Сервер работодателя пока не предоставлен. Инструкция для отдельного тестового окружения: deployment/RUN_LOAD_ON_SERVER_RU.md. Проверка на нём ещё не проводилась.

## 16 ноября 2026: курсы с тестами и заданиями

### Почему прежний замер не видел проблему

В прежнем сценарии уроки содержали только текст. Флаг `BENCH_ACTIVITIES=1` добавляет в каждый урок тест и задание, в каждый курс — контрольный тест, а ученикам — завершённую попытку и проверенную работу. В таком сценарии «Моё обучение» на старом коде выполняло **2201 SQL-запрос** на одно открытие (10 курсов) и отвечало 6,9–7,3 с даже без нагрузки.

Причина — N+1: для каждого теста и задания отдельно перепроверялись права, расписание группы, продление, последняя сдача и попытки; для каждого урока — условие «завершите предыдущий модуль»; для каждого курса — дедлайны модулей и права преподавателя.

### Изменения

1. `2c8e4de` — расписания, продления, сдачи и попытки загружаются одним запросом на таблицу; размещения тестов/заданий предзагружаются; предыдущий модуль проверяется один раз на модуль; контрольные тесты — одним запросом.
2. `4c496d3` — дедлайны модулей (`module_deadline_states_many`) и права преподавателя (`managed_run_ids`) считаются один раз для всех курсов ученика.
3. `921bcf4` — сценарий с тестами и заданиями; Sentry в нагрузочном тесте всегда отключён.

Правильность: ответы `my-learning`, `agenda`, страниц курсов и учебного плана преподавателя совпали байт в байт с записанными до изменений на сценарии с закрытыми модулями, контрольными тестами, продлениями, старыми уроками без шагов и всеми состояниями заданий. Тесты в `learning/test_performance.py` падают, если число запросов снова начнёт расти с числом уроков, тестов или курсов.

### Результат

100 клиентов, Redis, 8 потоков, 30 секунд, тот же генератор и та же машина для всех вариантов.

|---|---:|---:|---:|

| Одиночный ответ «Моё обучение» | 6,9–7,3 с | 0,24 с | 0,17–0,33 с |

### Что ограничивает дальше

Пропускная способность не изменилась (~18 запросов/с): предел задаёт среда. Под нагрузкой 30 SQL «Моего обучения» занимают ~0,8 с (~27 мс на запрос), без нагрузки — 0,08 с. PostgreSQL работает в Windows, приложение обращается к нему из Docker через `host.docker.internal`. Основная часть ответа — ожидание в очереди (6–8,7 с вне приложения при 8 потоках). Готовность к 100 одновременным ученикам на ноутбуке не подтверждена; следующий шаг — PostgreSQL рядом с приложением и замер на сервере.

## 16 ноября 2026: Gunicorn вместо Waitress

Предыдущий замер упирался в один процесс Python (GIL): ~18 запросов/с при любых оптимизациях и 6–8 с ожидания в очереди. Контейнер переведён на Gunicorn (`backend/gunicorn.conf.py`, gthread, 4 процесса × 4 потока). Waitress остаётся только для режима «Поделиться» в Windows.

Gunicorn не подставляет IP клиента из `X-Forwarded-For`. Это делает `config/proxy_wsgi.py`: берётся только последний адрес, дописанный Nginx, значения клиента левее игнорируются. На этом IP держатся защита входа и лимиты восстановления пароля. Лимит одновременных проверок кода считается на процесс, поэтому в контейнере `LMS_CODEJUDGE_SLOTS=1` (итого 4).

Условия те же: 100 клиентов, Redis, `BENCH_ACTIVITIES=1`, PostgreSQL в Windows, 30 секунд, таймаут 12 с, Docker с 4 CPU. Прогоны чередовались.

| | Waitress, 8 потоков | Gunicorn, 4 × 4 |
|---|---:|---:|
| Запросов/секунду | 17,0 / 17,0 | **30,3 / 28,5** |
| Ошибки (таймаут 12 с) | 75 / 96 | **0 / 1** |
| Всего ответов | 712 / 542 | 1011 / 967 |
| Отдано «Моё обучение» | 160 / 63 | 241 / 230 |
| Отдано «Структура курса» | 77 / 42 | 212 / 205 |
| p50 / p95 | 3,1–3,4 с / ≥12 с | 2,2–2,7 с / 6,2–8,4 с |
| Ожидание вне приложения, «Моё обучение» | 6,0–6,2 с | 2,9–3,1 с |

Пропускная способность выросла в 1,7 раза, ошибки исчезли. Время внутри приложения почти не изменилось (1,1–1,2 с на «Моё обучение» под нагрузкой). Дальнейший предел — 4 CPU ноутбука, на которых одновременно работают приложение, генератор нагрузки и PostgreSQL. Рабочий контейнер после перехода занимает ~254 МБ из 768.

Повторить: `BENCH_SERVER=gunicorn BENCH_WORKERS=4 BENCH_THREADS=4` (см. `deployment/RUN_LOAD_ON_SERVER_RU.md`). Отчёты: `.local/loadreports/test_btbs_load_20261116170907.json`, `…171256.json` (Waitress), `…171104.json`, `…171445.json` (Gunicorn).

## 17 ноября 2026: индексы и страницы групп на 2000 учеников

Инструмент: `backend/explain_probe.py`. Создаёт временную базу `test_btbs_explain_*` (2000 учеников, 20 курсов, 10 000 записей на курсы, ~300 000 отметок прогресса, по ~100 000 работ, попыток и снимков, 200 000 уведомлений, 300 000 событий аналитики), открывает основные страницы ученика, преподавателя и администратора и выполняет `EXPLAIN (ANALYZE, BUFFERS)` для каждого SELECT. После прогона база удаляется. Отчёты: `.local/explain/`.

### Вывод про индексы

Отдельные запросы быстрые. Время SQL на странице не превышало 1,2 с даже там, где ответ шёл 57 с. Полное чтение больших таблиц нашлось только в обзорах администратора. Добавлен один индекс: `submission_awaiting_review` (частичный, `review_due_at WHERE status='submitted'`) для очереди проверки и обзора. Чтения `courses_enrollment` без фильтра или по статусу, который есть почти у всех строк, индексом не ускоряются.

### Страницы с N+1

| Страница | Запросов до → после | Ответ до → после |
|---|---:|---:|
| Курс у ученика (`/api/study/courses/<id>/`) | 5488 → 30 | 5,9 с → 0,06 с |
| Отчёт по курсу | 688 → 18 | 6,3 с → 0,22 с |
| Главная преподавателя (`/api/workspace/home/`) | 9000 → 30 | 57 с → 4,0 с |
| Аналитика администратора | 251 → 42 | 19,7 с → 9,8 с |

Что было:
- Страница курса для каждого задания и теста загружала работы и попытки всех учеников. Теперь загружаются только записи этой группы, а для ученика только его собственные.
- Блок «Требуют внимания» вызывал `student_tasks()` для каждого ученика. Теперь `load_task_sources` и `tasks_by_enrollment` считают сроки для всех учеников сразу, права проверяются через `managed_enrollment_ids`.
- Отчёт считал прогресс по одному ученику и искал оценки перебором всех работ (ученики × задания × работы).
- Аналитика загружала все попытки, работы и решения ради 15 уроков текущей страницы и считала очередь проверки отдельно для каждого ученика и преподавателя.

Правильность: ответы всех четырёх страниц совпали байт в байт с записанными до изменений, для ученика, владельца курса, редактора, преподавателя группы и администратора. Сценарий включал закрытые модули, переносы сроков, работы на всех этапах проверки, задачи Python и правила внимания с обеими причинами. Тесты `GroupPageScalingTests` в `learning/test_performance.py` падают на старом коде.

Остаётся: главная преподавателя (4 с на ~2000 записей в его группах) и аналитика администратора (9,8 с на все 10 000 записей) тратят время в Python на расчёт сроков и прогресса по всем ученикам сразу. Следующий шаг — хранить готовый прогресс и сроки, которые обновляет Celery, вместо расчёта при каждом открытии страницы. Проверка обязательного предыдущего модуля по-прежнему делается отдельно для каждого ученика.
