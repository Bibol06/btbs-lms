# Фоновые задачи (Celery)

В Docker-стеке (`deployment/compose.yaml`) фоновая работа вынесена из веб-процесса:

| Сервис | Что делает |
|---|---|
| `worker-judge` | Проверка кода студентов, очередь `judge`, не больше 2 программ одновременно |
| `worker` | Периодические задачи, очередь `celery` |
| `beat` | Расписание из `CELERY_BEAT_SCHEDULE` в `backend/config/settings.py`. Должен быть ровно один |
| `redis` | Брокер (база 2) и кэш (база 1) |

## Расписание

| Задача | Интервал | Раньше |
|---|---|---|
| Закрытие тестов с истёкшим временем, напоминания о сроках | 30 с | `notification_worker` |
| Письма восстановления пароля | 15 с | `maintenance_worker` |
| Снимки прогресса для аналитики | 60 с | `analytics_snapshots --loop` |
| Очистка просроченных загрузок S3 и отложенных удалений | 1 ч | `cleanup_media_uploads` |

Если прошлый запуск задачи ещё не закончился, следующий пропускается (блокировка в Redis, `backend/background.py`). Запуски, накопившиеся, пока воркеры были остановлены, отбрасываются (`expires`), а не выполняются все подряд.

Бэкапы остаются в Планировщике Windows (`Install-LMS-BackupTask.ps1`): `pg_dump` 18 установлен на компьютере, в образе его нет. На сервере их стоит перенести в Beat вместе с PostgreSQL.

## Проверка кода

1. `POST /api/code/problems/<id>/execute/` создаёт отправку и ставит её в очередь. Ответ 202 с `id` (отправка) или `run_token` (пробный запуск).
2. Фронтенд опрашивает `GET /api/code/submissions/<id>/` или `GET /api/code/runs/<token>/`. Результат видит только автор.
3. Проверка, которая не началась за 90 с или не закончилась за 2 минуты, становится `service_error` и не тратит попытку.
4. У каждого пользователя одновременно может выполняться только один пробный запуск, поэтому общую очередь нельзя забить пробными запусками.

Среда Python монтируется только для чтения из `.local/runtime` (`LMS_CODE_RUNTIME`). Первая проверка после пересоздания контейнера компилирует среду (~7 с), дальше ~1 с.

## Без Docker (Windows, тесты)

Если `LMS_CELERY_BROKER_URL` не задан, задачи выполняются сразу внутри запроса, как раньше: API отвечает 200 с результатом. `Start-LMS.ps1` по-прежнему запускает команды-циклы, они вызывают те же функции.

## Команды

```sh
docker compose -f deployment/compose.yaml up -d
docker compose -f deployment/compose.yaml logs -f worker-judge
docker compose -f deployment/compose.yaml exec worker celery -A config inspect active
```

Redis использует `volatile-lru`: вытесняются только ключи кэша, у которых есть срок жизни, а очереди Celery никогда. Redis не сохраняет данные на диск. После его перезапуска проверки, стоявшие в очереди, станут `service_error` и не потратят попытку.
