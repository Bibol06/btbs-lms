# Повторение нагрузки на сервере работодателя

Сервер ещё не предоставлен. Ни один тест на сервере работодателя не выполнялся.

## Подготовка

1. Развернуть отдельную тестовую копию проекта на Linux с Docker и PostgreSQL. Не использовать рабочую базу учеников.
2. Указать параметры тестового PostgreSQL в отдельном backend/.env. Пользователь базы должен иметь право создавать временные базы. Почтовый backend в нагрузочном сценарии принудительно локальный, пользовательские данные не используются.
3. В deployment/compose.load.yaml заменить DB_HOST и extra_hosts на адрес тестового PostgreSQL. Не открывать PostgreSQL, Redis и диагностический порт 18765 в интернет. Nginx теста также не публикует внешний порт.
4. Собрать образы: `docker compose -f deployment/compose.yaml build web nginx`. Проверить свободное место (минимум 5 ГБ), CPU/RAM и отсутствие одновременно запущенных тяжёлых задач.

## Сравнение

```sh
BENCH_REDIS_URL=redis://cache:6379/1 BENCH_THREADS=8 docker compose -f deployment/compose.load.yaml up -d
docker compose -f deployment/compose.load.yaml logs -f probe
```

Дождаться `Report saved; disposable database cleanup finished.` и завершения probe с кодом 0. Только после этого запускать следующий прогон. Отчёты находятся в .local/loadreports. Повторить с BENCH_THREADS=16, затем при необходимости с BENCH_REDIS_URL='' (локальный кэш). Для каждого варианта сделать минимум два последовательных прогона в одинаковых условиях. Не совмещать с копированием, сборкой или видеозагрузками.

Реалистичный сценарий: добавить `BENCH_ACTIVITIES=1`. Тогда в каждом уроке появляются тест и задание, в каждом курсе — контрольный тест, а у учеников — завершённые попытки и проверенные работы. Без флага курсы содержат только текст, и расчёт сроков/заданий почти не нагружается. Sentry в нагрузочном тесте всегда отключён, чтобы синтетические ошибки не попадали в рабочий мониторинг.

После завершения: `docker compose -f deployment/compose.load.yaml down`. Команда не должна прерывать ещё работающий probe: именно он удаляет временную базу. Проверять test_database_removed=true в отчёте.

## Что означают цифры

- p95: 95% запросов уложились в это время; меньше лучше.
- rps: выполненные запросы в секунду. Вместе с ним смотреть errors.
- app_mean_ms: среднее время внутри Django до подготовки заголовков.
- sql_mean_ms: время обращений к PostgreSQL, включая ожидание и передачу данных. Это не чистое время вычислений СУБД.
- outside_app_mean_ms: остаток общего времени; очередь, сеть, Nginx и чтение ответа. Нельзя приписывать весь остаток исключительно очереди.
- *-profile.txt: функции, которые заняли больше всего времени в отдельном прогретом последовательном профиле.

Генератор работает отдельным процессом, но на той же машине. Это диагностический стенд; перед обещанием конкретного числа учеников нужен генератор на другом хосте, реалистичная пауза между действиями и сценарии входа/сдачи/просмотра. Текущий сценарий проверяет 100 авторизованных клиентов и четыре GET-маршрута; он не проверяет 1000 учеников, хеширование паролей, сдачу работ и видео.

Тест создаёт test_btbs_load_* и удаляет только свою базу. Профиль и отчёт не содержат паролей, session cookies или подписанных ссылок. Диагностические заголовки существуют только в нагрузочном WSGI-обёртывании, в рабочую LMS они не добавляются.
